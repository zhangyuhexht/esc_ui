# EscUI 项目总览与迭代指南

> 面向后续开发与维护的「地图」：先读第 1~2 章建立全局观，再对照第 3~4 章看代码，动手前看第 6~7 章。
> 本文档对应 **2.0.0**，如与代码冲突，以代码为准。

---

## 1. 项目定位与当前形态

**EscUI** 是 Paper 服务端插件：在 ESC 暂停菜单里加一个「服务器链接」按钮，点开是一页游戏内菜单。当前发布的默认配置里，这一页有 **5 个条目，全部是网址跳转**：

```
玩家按 ESC
   └─ 点「服务器链接」（插件注册的按钮）
        └─ 一页菜单（Dialog）：
             ├─ 服务器官网    → https://zhangyuhexht.top/
             ├─ 服务器文档    → https://zhangyuhexht.top/#/docs
             ├─ 粘液科技信息  → https://zhangyuhexht.top/#/slime
             ├─ 服务器规则    → https://zhangyuhexht.top/#/rules
             └─ 反馈/提议     → https://zhangyuhexht.top/#/feedback
```

代码还保留一条**未在默认配置中启用**的能力：条目写 `show-rules: true` 时，点击不跳网页，而是由服务端现场构建一个纯文本对话框（`rules` 段提供文字）。这条能力曾用于「服务器规则」按钮，后来规则改为网页，配置里的 `rules` 段被移除，但代码路径完整保留。

**技术路线**：Minecraft 的 Dialog 机制。引导阶段把「菜单页」注册进对话框注册表并挂进 `PAUSE_SCREEN_ADDITIONS` 标签 → ESC 出按钮；规则页（如果使用）不注册，玩家点击时由服务端现场构建 → 文本改完不用重启。

**为什么不用原生「服务器链接」**：原生 ServerLinks 列表每条只能是「名字 + 网址」，放不了自定义文本、也做不了更复杂的菜单结构。Dialog 自己注册，功能上限更高。代价是菜单页必须在启动引导阶段注册，改条目要重启。

## 2. 整体架构

```
┌────────────────────── 服务端插件（交付物 EscUI-2.0.0.jar）──────────────────────┐
│                                                                                │
│  服务端启动                                                                     │
│  ├─ ① 引导阶段 Bootstrap（注册表构建期，比 onEnable 更早）                     │
│  │    EscUIBootstrap.bootstrap()                                               │
│  │      ├─ MenuConfig.load() 读 menu.yml（缺文件时从 jar 释放默认配置）        │
│  │      ├─ 把「菜单页」注册进对话框注册表（key = escui:menu）                  │
│  │      └─ 加进 PAUSE_SCREEN_ADDITIONS 标签 → ESC 出现「服务器链接」按钮       │
│  │                                                                             │
│  └─ ② 运行期 onEnable                                                           │
│       EscUIPlugin.onEnable()                                                    │
│         ├─ 注册 PlayerCustomClickEvent 监听                                    │
│         └─ 自检：运行期构建一次规则对话框，确认这条链路可用                     │
│                                                                                │
│  游戏运行中                                                                     │
│  ├─ 点网址条目 → 客户端 staticAction(openUrl) 直接弹确认框并打开浏览器         │
│  │               （不经过服务端）                                              │
│  └─ 点 show-rules 条目 → customClick(escui:open/rules) 回调服务端             │
│       → 重读 menu.yml 的 rules 段 → 现场构建 → player.showDialog()              │
└────────────────────────────────────────────────────────────────────────────────┘
```

**关键 API 链**（Paper 26.2 API）：

```
注册对话框：RegistryEvents.DIALOG.compose().newHandler(event ->
               event.registry().register(DialogKeys.create(key), builder -> ...))
挂 ESC 按钮：LifecycleEvents.TAGS.preFlatten(RegistryKey.DIALOG)
               .newHandler(event -> event.registrar().addToTag(
                   DialogTagKeys.PAUSE_SCREEN_ADDITIONS,
                   List.of(TagEntry.valueEntry(DialogKeys.create(key)))))
网址动作：  DialogAction.staticAction(ClickEvent.openUrl(url))
文本动作：  DialogAction.customClick(Key.key("escui", "open/rules"), null)
运行期构建：Dialog.create(factory -> ...) → player.showDialog(dialog)
服务端回调：PlayerCustomClickEvent → PlayerGameConnection → Player
```

**两个类加载器**：引导类和主类跑在不同类加载器里，`DialogBuilder` 会被各自加载一份，所以它不能依赖任何静态共享状态（当前实现是无状态静态工具，符合这个约束）。

## 3. 代码走读

| 文件 | 职责 |
| --- | --- |
| `EscUIBootstrap.java` | `bootstrap(BootstrapContext)`：读配置 → 注册菜单页对话框 → 挂 ESC 标签。没有可用条目时只打 warning，ESC 不出按钮（合理降级）。 |
| `EscUIPlugin.java` | `onEnable()` 注册监听 + 运行期自检；`onCustomClick()` 只处理 namespace=`escui`、value 以 `open/` 开头的点击，目前只认 `rules`。 |
| `DialogBuilder.java` | 配置 → 对话框。`applyMenu()` 填注册表 builder；`buildRulesDialog()` 运行期现场构建；`actionOf()` 决定条目是开网址还是回调服务端。 |
| `config/MenuConfig.java` | 唯一配置入口，解析 `menu` + `rules`；文件不存在时从 jar 释放默认 `menu.yml`；永远返回对象，不会抛到调用方。 |
| `config/MenuDefinition.java` | record：`title / button / columns / entries` |
| `config/MenuEntryDefinition.java` | record：`label / url / showRules` |
| `config/RulesDefinition.java` | record：`title / lines` |

几个容易踩的细节：

- **菜单页按钮列表不能为空**：`DialogType.multiAction` 要求至少一个 action，为空时 `DialogBuilder` 自动补一个「关闭」按钮。
- **条目动作优先级**：`url` 非空 → 开网址；否则 → 回调服务端显示 `rules`。两个都没写会在解析阶段被跳过并打 warning。
- **网址校验**：`URI.create()` + 必须带协议头，否则该条目被跳过。
- **纯文字、不碰物品**：对话框只用文字和按钮，避开引导阶段「物品注册表未绑定」导致 `new ItemStack()` 崩溃的老坑。
- **颜色码**：`LegacyComponentSerializer.legacyAmpersand()` 解析 `&` 格式码。
- **引导阶段注册是硬约束**：对话框只有在这个阶段注册才能挂进 ESC 标签，运行期补注册来不及 —— 这就是「改条目要重启」的根因。

## 4. menu.yml 配置格式

```yaml
menu:
  title: "服务器链接"          # 点开后的标题（缺省「服务器链接」）
  button: "服务器链接"         # ESC 按钮文字（缺省同上）
  columns: 1                  # 列数 1~4（缺省 1，超出范围会被钳制）
  entries:
    - label: "服务器官网"       # 必填，按钮文字
      url: "https://zhangyuhexht.top/"        # 动作 A：开网页
    # - label: "服务器规则"
    #   show-rules: true       # 动作 B：显示 rules 段文本（与 url 二选一）

# 动作 B 需要配套的文字（当前默认配置未启用）
# rules:
#   title: "服务器规则"
#   lines:
#     - "&f正文，一行一段，\"\" 表示空行"
```

规则：

- `menu.entries` 为空或全部解析失败 → 不注册 ESC 按钮（插件装了但菜单不出现）。
- 单条失败只跳过该条 + warning，不影响其它条目。
- `rules.lines` 为空 → `rules()` 返回 null；此时 `show-rules` 条目点击只会打 warning，不弹对话框。
- 支持 `&0-9a-f`、`&k-o`、`&l`、`&r`；避免 ✔ ✘ → 等生僻 Unicode（Minecraft 默认字体可能缺字形），用【】、· 等常见字符。
- 网址带 `#/xxx` 这类 SPA 哈希路由可以原样写。

## 5. 构建、测试与验证

```bash
# JDK 25
./gradlew build                       # 产物 build/libs/EscUI-2.0.0.jar
bash scripts/setup-testserver.sh      # 下载 Paper、写 eula/配置、放入 jar、清旧版本 jar
bash scripts/run-testserver.sh        # 启动 → 等 "Done (" → 自动 stop → PASS/FAIL
```

- 构建依赖：`paper-api:26.2.build.129-stable`、`placeholderapi:2.12.3`，两者都是 `compileOnly`。
- `processResources` 把 `${version}` 注入 `paper-plugin.yml`；编译用 `options.release = 25`、UTF-8、`-Xlint:deprecation`。
- 测试脚本：默认 Paper 26.2、端口 25599、离线模式、flat 世界；`PAPER_VERSION=26.3` 可切换；判定标准是日志出现 `Done (` 且无 `SEVERE|Exception|Ambiguous`。
- **Paper 26.3 实测通过**：EscUI 2.0.0 加载正常、5 个条目注册、`Done (7.563s)`、零插件报错；`api-version: 26.2` 被 26.3 正常接受。
- 测试目录里**不能同时放两个同名插件 jar**（Paper 会报 `Ambiguous plugin name`），`setup-testserver.sh` 会自动清旧版本。
- 改完代码务必重新执行 `setup-testserver.sh` 部署再测，否则容易拿旧 jar 误判。

> 服务端脚本能验证的是「插件加载无报错、菜单注册成功、对话框能构建」。按钮实际渲染、点击后是否开浏览器、规则文本显示效果，需要进游戏确认。

## 6. 已知限制

1. **菜单结构改动要重启**：条目增减、改名、网址、列数、ESC 按钮文字都在引导阶段固化；只有 `rules` 文本是点击时重读、热生效。
2. **客户端版本**：Dialog 是较新版本的原生特性，旧客户端无法回退显示（Via 系插件也没法把 Dialog 翻译成旧协议界面）。
3. **文本字体**：生僻 Unicode 符号可能显示成方框。
4. **PlaceholderAPI 依赖未被使用**：`build.gradle.kts` 里 compileOnly 了 PAPI 2.12.3，源码零引用、`paper-plugin.yml` 也没有 `softdepend`。要么实现占位符支持，要么移除依赖。
5. **缺少客户端实测闭环**：目前验证止于服务端加载与注册日志。
6. **描述文案与现状有小偏差**：`paper-plugin.yml` 的 `description` 仍提到「游戏内服务器规则文本」，那是上一版形态；纯描述性文本，不影响功能。

## 7. 迭代方向

1. **客户端实测**：进游戏过一遍 ESC 按钮 → 5 个条目渲染 → 每个网址是否正确打开；若启用 `show-rules`，再验文本对话框的显示与滚动。
2. **PAPI 去留**：移除无用依赖，或让标题/按钮/tooltip 支持 `%xxx%` 占位符。
3. **菜单热重载**：现状结构上无法在运行期改注册表；若确实需要，可把菜单页也改成「注册一个极简壳 + 点击时运行期构建」，代价是多一跳、且 ESC 标签里仍要有一个壳。
4. **扩展页面类型**：照 `show-rules` 的模式加页面（`openKey(page)` 已支持任意页面名，在 `EscUIPlugin.onCustomClick` 里按 page 分派即可）。
5. **配置校验加强**：启动时校验 `show-rules` 条目是否配套 `rules` 段、label 重复、网址协议头等，把 warning 前置。
6. **内容硬编码**：如果菜单内容不再需要服主修改，可以把 `MenuConfig` 换成代码里直接构造 `MenuDefinition`，删掉 YAML 解析（改动很小）。

## 8. 关键设计决策速查

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| ESC 入口 | 自定义 Dialog 按钮 | 原生 ServerLinks 放不了文本，也做不了自定义菜单结构 |
| 菜单页注册时机 | 引导阶段 bootstrapper + `PAUSE_SCREEN_ADDITIONS` | 只有这个阶段能注册对话框并挂 ESC 标签 |
| 规则页构建时机 | 点击时运行期构建、不注册 | 文本改完不用重启 |
| 网址按钮 | `staticAction(ClickEvent.openUrl)` | 客户端直接完成，服务端零参与 |
| 文本按钮 | `customClick(escui:open/rules)` | 需要服务端现场构建对话框 |
| 不含物品 | 纯文字 + 按钮 | 避开引导期物品注册表未绑定的崩溃 |
| 空条目列表 | 不注册按钮 + warning；builder 层补「关闭」 | 合理降级 + 满足 Dialog 至少一个 action |
| 单条配置失败 | 跳过该条 + warning | 一条写错不影响其它条目 |
| 配置加载失败 | 返回空对象而非抛异常 | 插件永远能启用，故障表现为菜单不出现 |
